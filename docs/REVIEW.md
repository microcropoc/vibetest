## Замечания

### Высокий приоритет (технические риски)

1. **vt-2 — конвертер JSON Schema → Zod может не покрыть наши схемы.** Схемы используют: `if`/`then` для дискриминации `content` по `type` (обе схемы, `allOf` из 6 веток), внешние `$ref` (`./course.schema.json#/$defs/uuid` и `$defs/*Content` из import-схемы), `uniqueItems` (quiz). Популярные конвертеры (например, json-schema-to-zod) `if/then` не поддерживают. Spike в карточке предусмотрен — это правильный первый шаг. Зафиксировать fallback заранее: ручной `z.discriminatedUnion('type', …)` поверх сгенерированных частей + типы через json-schema-to-typescript + smoke-тест эквивалентности Zod ↔ JSON Schema через Ajv на общих фикстурах.
2. **Абсолютные `$id` в схемах ломают офлайн-резолв `$ref`.** Обе схемы имеют `$id: "https://vibetest.app/schemas/…"`; `$ref: "./course.schema.json"` по спецификации резолвится от базы `$id` в URL, а не в локальный файл — резолверы либо пойдут в сеть (ref-parser), либо упадут с «can't resolve reference» (Ajv). В vt-2: регистрировать обе схемы по `$id` (Ajv `addSchema`, кастомный resolver у bundler'а) и проверять генерацию офлайн. Альтернатива — убрать/сменить `$id` (но это правка `docs/schemas/`, выходит за рамки vt-2 — согласовать отдельно).
3. **vt-12: helper удаления прогресса должен быть транзакционно-композабельным.** vt-15 требует replace **одной** транзакцией (`deleteAllByCourseId` + `CourseRepository.put`). Если helper vt-12 будет сам открывать транзакцию только над `stepProgress`, в vt-15 его придётся переделывать. Дописать в требования vt-12: helper вызывается внутри внешней `db.transaction('rw', [courses, stepProgress], …)` (или принимает таблицу/контекст), сам транзакцию не открывает.

### Средний приоритет (уточнить в карточках)

4. **Strict TS в scaffold отсутствует.** Ни `tsconfig.json`, ни `tsconfig.app.json` не содержат `strict: true` (правило проекта strict требует). Закрывается требованием vt-2 — порядок корректный, но это подтверждает, что vt-2 должен идти первым кодовым изменением и никакой код до него писать нельзя.
5. **vt-2, semantic rule «reset без SQL INSERT/seed» — эвристика без точной дефиниции.** Поиск по подстроке даст false positives в JS-коде (`insertAdjacentHTML`, переменная `insert`). Определить точно (например, регистронезависимо, с границей слова `\bINSERT\b`/`\bINTO\b`) и зафиксировать в REPORT vt-2 — иначе проверка будет вести себя непредсказуемо для авторов курсов.
6. **vt-8: лимит «≤ 20 элементов» для args из спецификации не упомянут** в требованиях (только «validate JSON args array»). Добавить в чек-лист, чтобы не потерять при реализации.
7. **vt-9: sql.js требует `.wasm` как asset + `locateFile`.** Нужна правка `angular.json` (assets) — правило допускает при необходимости, но сейчас в карточке пункта нет. Добавить: подключение sql.js, раздача wasm, загрузка внутри Worker. (Кэширование WASM в vt-27 уже учтено.)
8. **vt-16: дефолтный `app.spec.ts` сломается.** Тест scaffold'а проверяет `h1` с «Hello, vibetest-app» — при замене шаблона на shell упадёт. Добавить в план vt-16 пункт «обновить/удалить дефолтный spec».
9. **Дублирование confirm-диалога.** vt-17 (удаление курса) и vt-24 (replace confirm) оба требуют диалог подтверждения; правило запрещает дублирование. Предложение: в vt-17 создать dumb `ConfirmDialogComponent` в `shared/ui/`, в vt-24 дописать «переиспользовать confirm из shared/ui».
