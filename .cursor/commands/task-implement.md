# Реализация задачи vt-*

Ввод пользователя: `$ARGUMENTS` (номер `vt-{n}`, slug, путь к backlog-файлу или описание — что указал пользователь).

Определи задачу однозначно. Если неоднозначно — уточни у пользователя.

Критерии кода и архитектуры — в `.cursor/rules/angular-cli.mdc`. Спецификация: `docs/SPECIFICATION.md`.

## Определение режима (первый шаг)

1. Если `$ARGUMENTS` пустой — определи `vt-{n}-{slug}` по текущей ветке `feature/vt-{n}-{slug}`.
2. Если папка `docs/tasks/in-progress/vt-{n}-{slug}/` уже существует — **сначала прочитай только `REPORT.md`** (не открывай `TASK.md` и `docs/SPECIFICATION.md` до выбора режима).
3. Выбери режим:
   - **Режим Б (правки после ревью):** в `## Изменения по ревью` есть незакрытые замечания последнего раунда (пункты без соответствующего блока `### Что исправлено` для этого раунда), **или** пользователь явно просит исправить ревью.
   - **Режим А (первичная реализация / продолжение по TASK):** задача ещё в `backlog/`, или в `## Изменения по ревью` нет открытых замечаний (только «Замечаний нет» / все раунды закрыты блоками «Что исправлено»).

## Режим Б — правки после ревью

1. Работай **только** по пунктам последнего незакрытого раунда в `## Изменения по ревью`.
2. **Не перечитывай** `TASK.md` и `docs/SPECIFICATION.md` целиком; обращайся к ним только если конкретное замечание явно ссылается на требование оттуда.
3. Прочитай файлы, указанные в замечаниях; исправь код и добавь/обнови тесты по необходимости.
4. **Protected app:** правки в `vibetest-app/` только на ветке `feature/vt-{n}-{slug}` при существующей папке in-progress для этой задачи.
5. Допиши в `REPORT.md` под замечаниями текущего раунда подсекцию `### Что исправлено` (или `### Что исправлено (раунд N)`). **Не переписывай** другие секции REPORT, кроме «Что исправлено» для этого раунда.
6. Перед завершением: `ng test --watch=false` в `vibetest-app/`, если менялся код или тесты.
7. **Коммит на feature-ветке:** закоммить все изменения. Сообщение: `vt-{n}: {кратко про фиксы ревью}`. Если изменений нет — коммит не нужен.

## Режим А — первичная реализация

### Старт (если задача ещё в backlog)

1. Найди `docs/tasks/backlog/vt-{n}-{slug}.md` (или создай in-progress из указанного файла).
2. Создай папку `docs/tasks/in-progress/vt-{n}-{slug}/`.
3. Перемести содержимое backlog в `TASK.md` (удали backlog-файл после переноса).
4. Создай `REPORT.md` из `docs/tasks/_template/REPORT.md`: frontmatter `branch: feature/vt-{n}-{slug}`, заголовок и плейсхолдеры по задаче.
5. Ветка: `git switch main` (актуализируй), `git switch -c feature/vt-{n}-{slug}`.
6. Одна задача — одна feature-ветка.

### Реализация

1. Прочитай `TASK.md`, релевантные разделы `docs/SPECIFICATION.md`, `REPORT.md`.
2. **Protected app:** правки в `vibetest-app/` только на этой ветке при существующей папке in-progress для этой задачи.
3. Реализуй по TASK; соблюдай smart/dumb, domain folders, strict TS, signals, тесты где уместно.
4. Обновляй `REPORT.md` (все секции **кроме** «Изменения по ревью» — по ходу работы).
5. Перед завершением: `ng test --watch=false` в `vibetest-app/`, если менялась логика с существующими тестами или добавлена нетривиальная логика.
6. **Коммит на feature-ветке (обязательно):** закоммить все изменения задачи в **локальную** ветку `feature/vt-{n}-{slug}`. Сообщение: `vt-{n}: {краткое описание}`. Если изменений нет — коммит не нужен.

## Запрещено без явного запроса

- Merge, squash, push, перенос `in-progress/` → `done/` (используй `/task-merge`)
- Правки `vibetest-app/` на `main` или без matching in-progress

## Ответ в чате

Укажи **режим (А или Б)**. Краткий статус: ветка, что сделано, тесты, **хеш последнего коммита** (если был). В режиме А — что осталось по TASK; в режиме Б — какие пункты ревью закрыты.
